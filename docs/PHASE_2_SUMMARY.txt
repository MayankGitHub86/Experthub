═══════════════════════════════════════════════════════════════════════════════
THE ATOMIC RESERVATION SYSTEM (ReservationUnit)
═══════════════════════════════════════════════════════════════════════════════

PROBLEM SOLVED:
  The original unique index {expertId, startTime, endTime, status}
  allowed partial overlaps:
    10:00-11:00 and 10:30-11:30 both allowed (different values)
    This is a CRITICAL FLAW allowing double-booking

SOLUTION IMPLEMENTED:
  Fixed-granularity slots (15 minutes each)
  One 60-minute booking occupies 6 slots:
    09:45 (buffer before)
    10:00, 10:15, 10:30, 10:45 (booking)
    11:00 (buffer after)

  Unique compound index: {expertId, slotDateTime}
  With partial filter: {status: {$in: ['held', 'confirmed']}}

HOW IT WORKS:
  1. Generate all 15-min slots the booking will occupy
  2. Call ReservationUnit.insertMany(units, {ordered: true})
  3. If ANY unit conflicts → E11000 error → entire operation fails
  4. Either ALL units created OR NONE (atomic)
  5. Conflicts on buffer times prevent adjacent bookings

VERIFICATION:
  ✓ 20 concurrent requests to 10:00-11:00
  ✓ Exactly 1 succeeds, 19 rejected
  ✓ No orphaned reservation units
  ✓ Database state consistent
  ✓ Conflict errors properly reported
